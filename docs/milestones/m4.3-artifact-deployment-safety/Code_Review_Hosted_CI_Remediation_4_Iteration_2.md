## 2. 필수 수정 사항

### CR-HCI4-I2-MAJ-01 — `--verify`가 line 3 이후 unexpected/duplicate header evidence를 제거하고 PASS함

**위치:** `scripts/compile_lock.sh:85-109`, `scripts/compile_lock.sh:138-150`  
**관련 test 공백:** `tests/unit/test_compile_lock_header_contract.py:192-238`

`validate_committed_header()`는 커밋된 파일의 1번째 줄과 2번째 줄만
검사한다. exact uv 0.8.15 autogenerated header는 두 줄이어야 하지만,
3번째 줄 이후에 추가된 임의 comment/header 또는 두 번째 autogenerated
banner를 거부하지 않는다. 그 뒤 `canonical_body()`가 모든 선행 `#` 줄을
제거하므로 이 증거는 body hash 비교에서 사라지고 `--verify PASS`가 된다.

독립 fake-uv probe에서 canonical lock의 line 3에 각각 아래 값을 삽입한 뒤
`--verify`를 실행했다.

| 변조 | 실제 결과 | 기대 결과 |
|---|---|---|
| `# unexpected third header line` | exit 0, `--verify PASS` | nonzero |
| canonical autogenerated banner 중복 | exit 0, `--verify PASS` | nonzero |

이는 이번 Task가 요구한 missing/moved/malformed/**duplicate/unexpected** header의
exact fail-closed grammar와 “`--verify`가 header evidence를 지우지 않아야 한다”는
계약을 직접 위반한다. generated scratch output의 `validate_and_normalize_header()`도
line 3 이후 canonical banner prefix 중복만 찾고 임의의 unexpected leading
comment/header는 허용하므로, canonical compile 산출물 자체도 exact two-line
grammar가 아니다.

**필수 조치:**

1. generated output과 committed lock 모두에서 line 1/2가 exact expected 값이고,
   line 3이 첫 body line임을 검증해 추가 leading comment/header를 전부 거부한다.
2. committed lock에도 duplicate banner 검사를 포함하되, 별도 부분 검사보다
   하나의 exact two-line header validator를 재사용해 두 경계가 다시 갈라지지
   않게 한다.
3. fake-uv compile test에 arbitrary unexpected third header를, `--verify` test에
   unexpected third header와 duplicate banner 변조를 추가하고 모두 nonzero를
   요구한다.

## 3. 폐쇄가 확인된 범위

### 3.1 canonicalization과 기존 malformed 경계

- uv 0.8.15의 line 1 banner와 line 2 command prefix를 exact 문자열로 고정하고,
  `-o` 값 누락/공백 trailing token/flag 누락/line 이동/wrong banner를 nonzero로
  거부한다.
- 검증 성공 후 line 2를 `-o requirements.lock`으로 치환하고 exact post-check를
  수행하므로 scratch pathname은 정상 경로에서 안정적으로 제거된다.
- 반복 compile의 byte-for-byte 안정성 test와 committed line 1/2 변조 test는
  실제 구현 결함을 검출하는 assertion을 갖는다. 다만 위 line 3 경계를 생성하지
  않아 remaining defect를 검출하지 못한다.

### 3.2 lock body와 index 의미론

- `b072fc9` 대비 package body 변화는 앞선 리뷰와 동일하게 `filelock`
  `3.32.2 -> 3.32.3`, `uvicorn` `0.52.2 -> 0.52.3` 및 대응 hash 교체다.
- `--extra-index-url https://download.pytorch.org/whl/cpu`,
  `--index-strategy unsafe-best-match`, `--generate-hashes`, `--no-annotate`와
  body reproducibility/drift hash 비교는 유지됐다. CPU torch/index 경계의
  의미론을 바꾸는 diff는 없다.
- 현재 `requirements.lock` line 2는 canonical `-o requirements.lock`이며,
  보고된 linux/amd64 Python 3.11 + `uv==0.8.15` compile/verify evidence와
  full-suite evidence 사이에 상충하는 기록은 발견하지 못했다. 다음 hosted
  native x64 verify는 여전히 push 이후 필요한 receipt다.

### 3.3 positive readiness 60초와 negative fail-closed 경계

- `scripts/container_smoke.py`는 positive `expect_status=200` 호출만
  `max_seconds=60`으로 확장한다. 상태 코드/응답 판정, 후속 mock query,

- negative seam은 기존 기본 10초, exact 503 및
  `artifact_test_embedding_seam_unavailable` reason을 유지한다. production
