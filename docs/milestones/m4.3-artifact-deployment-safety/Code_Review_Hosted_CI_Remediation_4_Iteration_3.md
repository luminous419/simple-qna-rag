## 2. 선행 MAJOR 폐쇄 검증

### 2.1 generated lock의 exact/bounded grammar와 canonical output

`scripts/compile_lock.sh`는 uv 산출물에 대해 다음 순서로 fail-closed한다.

1. line 1을 exact autogenerated banner와 비교한다.
2. line 2가 기존 compile 인자를 그대로 포함한 `HEADER_PREFIX`로 시작하는지 확인하고,
   마지막 `-o` 값이 비어 있거나 공백/trailing token을 포함하면 거부한다.
3. 정규화 전에 공용 `assert_no_extra_header_lines()`를 호출해 line 3 이후의 모든
   `#` line을 거부한다. 따라서 임의의 third comment와 전체 banner 중복이 body 비교로
   제거되기 전에 실패한다.
4. 검증을 통과한 경우에만 line 2를 exact
   `... -o requirements.lock`으로 치환하고, 치환 결과를 다시 exact 비교한다.

두 compile 모두 이 검사를 통과해야 body reproducibility 비교로 진행한다. scratch
경로는 최종 산출물에 남지 않으며 반복 실행 결과가 byte-for-byte 동일하다는 성공
테스트도 통과했다. malformed generated output은 committed lock을 만들기 전 실패하므로
기존 lock/index 산출 경계를 오염시키지 않는다.

### 2.2 committed lock 검증이 body 비교보다 먼저 수행됨

`--verify`는 새 두 lock의 header와 body reproducibility를 확인한 뒤, committed
`requirements.lock`의 line 1/2 exact canonical form 및 동일한
`assert_no_extra_header_lines()`를 먼저 검사한다. 그 다음에만 committed body hash를
비교한다. 따라서 stale scratch path, tampered banner, arbitrary third comment,
duplicated two-line banner가 `canonical_body()`에 의해 사라져 PASS하는 이전 두
fail-open 경로는 남아 있지 않다.

### 2.3 15개 fake-uv test와 mutation 검출력

현재 test 구성은 성공/canonical 안정성 2건, generated malformed 8개 parameter case,
committed verify 5건으로 총 15건이며 모두 PASS했다. 각 negative assertion은 nonzero
exit를 요구하고 generated malformed 경우 lock 미생성까지 확인한다.

독립 mutation probe는 workspace 밖 임시 복사본에서 generated/committed 경로의
`assert_no_extra_header_lines()` 호출 두 곳만 비활성화했다. 그 결과 아래 세 신규
회귀 test가 모두 실패했고, 스크립트가 실제로 exit 0 또는 `--verify PASS`를 냈다.

- generated `unexpected_third_header`
- committed arbitrary third header comment
- committed duplicated canonical banner

즉 신규 test는 구현과 같은 조건을 반복하는 형식적 assertion이 아니라 선행 리뷰가
재현한 결함 클래스를 실제로 검출한다.

## 4. `container_smoke.py` 60초 delta

diff는 positive readiness의 `_poll_ready(host_port, expect_status=200)` 한 호출에만
`max_seconds=60`을 전달한다. 200 status 요구, 후속 mock `/rag` query, live/root/static,
host gateway, image identity, graceful stop 및 `compute_all_ok()`의 boolean 판정은
변하지 않았다. 60초 내 ready 200이 없으면 여전히 `ready_ok=false`와 최종 FAIL이므로
실제 기동 실패를 성공으로 마스킹하지 않는다.

negative activation은 기존 기본 10초, exact 503 및
`artifact_test_embedding_seam_unavailable` reason을 그대로 사용한다. 따라서 production
test seam 봉인 경계는 완화되지 않았다. 보고된 linux/amd64 build/smoke PASS 및
hosted failure의 `live=true`, `ready=false`, `mock_query_ok=false` 패턴은 이 bounded
positive-only timeout 조정과 일치하지만, 실제 hosted timing 개선은 다음 run에서
확인해야 한다.
