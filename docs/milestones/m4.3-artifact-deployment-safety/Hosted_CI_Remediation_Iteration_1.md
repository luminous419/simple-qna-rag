## 1. `requirements.lock` drift

### 1.1 원인

`requirements.txt`가 `langsmith`/`sqlalchemy`/`typing-inspection`을
정확한 버전으로 pin하지 않으므로, 커밋 시점 이후 PyPI에 새 릴리스
(`langsmith` 0.10.17→0.10.18, `sqlalchemy` 2.0.51→2.0.52,
`typing-inspection` 0.4.3→0.4.4)가 올라오면서 hosted runner가
`uv pip compile`을 재실행할 때마다 다른 해를 얻게 됐다 — `compile_lock.sh
--verify`는 정확히 이 드리프트를 감지하도록 설계된 게이트(M4.1 §8.2)이므로
의도대로 실패했다.

### 1.2 수정

**주의**: 이 저장소는 이미 두 번(`d0b57d0`, `0eb09bf`) macOS에서 직접
`compile_lock.sh`를 실행해 lock이 macOS arm64 dependency graph로
오염되는 동일한 사고를 겪은 이력이 있다(`greenlet`이 macOS arm64에서는
`platform_machine` marker에 안 걸려 누락되는 등 — `d0b57d0` 커밋 메시지
참조). 이번 세션도 처음에는 같은 실수를 반복해 macOS에서 직접
`bash scripts/compile_lock.sh`를 실행했고, 그 결과 103개가 아닌 102개
패키지가 해석되는 것을 확인하고 즉시 `git checkout -- requirements.lock`으로
되돌렸다.

올바른 절차로 재실행했다: `docker run --rm --platform linux/amd64 -v
"$PWD":/work -w /work python:3.11-slim bash -c "pip install uv==0.8.15 &&
bash scripts/compile_lock.sh && bash scripts/compile_lock.sh --verify"` —
ubuntu-latest hosted runner와 동일한 linux/amd64 대상으로 컴파일하고, 같은
컨테이너 안에서 재현성(`--verify`)까지 확인했다. 결과: 103개 패키지 유지
(플랫폼 그래프 회귀 없음), `langsmith`/`sqlalchemy`/`typing-inspection` 3개
패키지만 버전·해시가 갱신됐다(diff는 위 3개 항목 + autogenerated 헤더의
임시 출력 경로 타임스탬프뿐).

`tests/unit/test_dependency_lock.py::test_lock_package_count_is_103`,
`tests/unit/test_dependency_snapshot.py`의 `package_count == 103` 두
하드코딩 값 모두 여전히 유효해 테스트 파일 수정은 필요 없었다.

## 2. `scan_image_layers.py` — CA 신뢰 저장소 false positive

### 2.1 원인

`FORBIDDEN_PATTERNS`의 `(".pem", "credential")` 항목은 경로 substring
매치만으로 판단했다 — 실제 컨테이너 credential(개인키, 애플리케이션
번들 인증서)과 base 이미지가 정상적으로 포함하는 OS/interpreter CA
신뢰 번들을 구분하지 않았다. hosted run의 실제 violation 153건을 조사한
결과 네 개 경로 그룹으로 전부 설명된다(`gh api .../jobs/94104542681/logs`
로 확인):

| 경로 패턴 | 출처 | 건수 |
|---|---|---|
| `etc/ssl/certs/*.pem` | Debian/Ubuntu 시스템 신뢰 저장소(개별 CA 파일) | 149 |
| `usr/lib/ssl/cert.pem` | OpenSSL 기본 신뢰 번들 위치(symlink) | 1 |
| `usr/local/lib/python3.11/site-packages/certifi/cacert.pem` | 최상위 `certifi` 패키지(transitive dep) | 1 |
| `usr/local/lib/python3.11/site-packages/pip/_vendor/certifi/cacert.pem` | `pip`에 vendored된 `certifi` 사본 | 1 |

네 그룹 모두 REQ-005.4("image에는 ... credential이 없어야 한다")가
막으려는 실제 위협(개인키, 앱 인증서, 시크릿)이 아니라 base 이미지가
HTTPS를 위해 정상적으로 요구하는 공개 CA 인증서다.

### 2.2 설계 — fail-closed 허용목록

허용은 두 조건을 **모두** 만족해야만 성립한다 — 하나라도 실패하면
기존과 동일하게 `credential`로 분류한다(즉 이 변경은 `.pem`/`.crt`가
보고하는 범위를 좁히기만 하고, 넓히지 않는다):

1. **경로**: 정규화된 경로가 알려진 OS/interpreter 신뢰 저장소 위치
   (`etc/ssl/certs/`, `usr/lib/ssl/`, `usr/share/ca-certificates/`,
   `etc/pki/tls/certs/`, `etc/pki/ca-trust/`, 또는 `*/certifi/cacert.pem`
   접미사)에 있고 확장자가 `.pem`/`.crt`여야 한다. 이 목록 밖의 경로(예:
   `app/secrets/*.pem`)는 콘텐츠가 무엇이든 여전히 `credential`이다 —
   "arbitrary app PEM credentials"가 여전히 걸리는 지점이다.
2. **콘텐츠**(경로 조건을 만족하는 일반 파일에만 적용): 새 함수
   `is_verified_ca_bundle()`이 (a) 파일 안의 모든 PEM 블록 라벨이 정확히
   `CERTIFICATE`인지(개인키/CSR/공개키 등 다른 라벨이 하나라도 있으면
   즉시 거부 — 진짜 CA 인증서와 개인키를 같은 파일에 이어붙이는 은닉
   시도를 막는다), (b) ASCII로 디코드되는지, (c)
   `ssl.SSLContext.load_verify_locations(cadata=...)`가 예외 없이
   받아들이는지(구조적으로 유효한 X.509 인증서인지 stdlib만으로 검증 —
   새 의존성을 추가하지 않았다)를 확인한다. 셋 중 하나라도 실패하면
   `False`를 반환해 기존 `credential` 분류로 떨어진다.

심볼릭 링크(`usr/lib/ssl/cert.pem` 등, tar member 자체는 콘텐츠가
없다)는 경로 조건만으로 예외 처리한다 — 링크가 가리키는 실제 파일은
그 자체가 별도 tar member로 스캔되므로 안전하다.

`classify_member()`의 시그니처에 선택적 `read_content`(콘텐츠 지연
로더)와 `is_symlink`를 추가했다. `scan()`은 멤버 경로가 허용목록 후보일
때만(즉 대부분의 파일은 여전히 경로 문자열 검사만으로 즉시 판정) 실제
tar에서 바이트를 읽으므로, 레이어당 최대 47,998개 멤버가 있는 이번
이미지에서도 콘텐츠 읽기는 153개 후보로 국한된다.

### 2.3 deletion-history leakage — 코드 변경 없음, 불변식 확인

OCI 레이어는 additive다: 나중 레이어의 whiteout(`.wh.*`)은 이전 레이어에
실제로 쓰인 바이트를 지우지 않는다. `scan()`은 애초에 각 레이어를
독립적으로(squash된 최종 뷰가 아니라) 순회하므로, 어떤 레이어에서
credential이 추가된 뒤 다음 레이어에서 whiteout으로 "삭제"돼도 그
credential이 실제로 쓰인 레이어에서는 여전히 정상 멤버로 분류된다 — 이
설계는 이번 remediation 이전부터 성립했고 코드 변경이 필요 없었다. 이
불변식을 명시적으로 고정하는 회귀 테스트
(`test_deleted_credential_still_detected_in_earlier_layer`)를
추가했고, 모듈 docstring에도 이 설계 근거를 적었다.

## 3. 신규 테스트

`tests/unit/test_scan_image_layers.py`에 14개 테스트를 추가했다(기존
6개 + 신규 14개 = 20개, 전부 PASS):

- **positive(허용돼야 함)**: 신뢰 저장소 경로의 실제 CA 인증서
  (`etc/ssl/certs/*.pem`), 최상위/vendored `certifi/cacert.pem` 2종,
  신뢰 저장소 경로의 symlink(콘텐츠 없이 경로만으로 허용).
- **negative(여전히 credential이어야 함)**: 신뢰 저장소 경로에 놓인
  가짜 개인키(`RSA PRIVATE KEY` 라벨), 신뢰 저장소 경로의 구조적으로
  깨진 `CERTIFICATE` 블록(`ssl` 파싱 실패), 신뢰 저장소 밖 경로에 놓인
  **진짜** CA 인증서 콘텐츠(경로 조건 미충족), 신뢰 저장소 밖의 개인키
  PEM, `.env`/`.pfx` 회귀 확인.
- **`is_verified_ca_bundle()` 단위 테스트**: 인증서+개인키 혼합 파일
  거부, PEM 블록이 전혀 없는 콘텐츠 거부, 다중 인증서 번들(certifi
  형식과 동일한 반복 `CERTIFICATE` 블록) 허용.
- **deletion-history leakage 회귀**: 위 §2.3.

모든 CA 콘텐츠 fixture는 실제 Mozilla 루트(Entrust Root Certification
Authority, `certifi`가 배포하는 실제 인증서 1개를 그대로 추출)를 사용해
`ssl.SSLContext.load_verify_locations`가 실제로 통과하는 바이트임을
보장했다 — 합성 base64를 그럴듯하게 잘라 붙인 fixture는 파싱 자체가
실패해 테스트가 거짓으로 통과할 위험이 있어 배제했다.
