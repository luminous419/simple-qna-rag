## 1. `requirements.lock` drift

### 1.1 원인

`requirements.txt`는 `filelock`/`uvicorn`을 정확한 버전으로 pin하지
않는다(`uvicorn>=0.24.0`, `filelock`은 `huggingface-hub`/`torch` 체인의
transitive dependency). 커밋된 lock 시점 이후 PyPI에 `filelock`
3.32.2→3.32.3, `uvicorn` 0.52.2→0.52.3 두 patch 릴리스가 올라오면서,
hosted runner가 `bash scripts/compile_lock.sh --verify`로 `uv pip
compile`을 재실행할 때마다 다른 해를 얻게 됐다 — `--verify`는 정확히 이
드리프트를 감지하도록 설계된 게이트(M4.1 §8.2)이므로 의도대로 실패했다.
hosted 로그(`gh api .../jobs/94549117179/logs`)로 확인: `pip install
--require-hashes`는 커밋된 lock 그대로(`filelock==3.32.2`,
`uvicorn==0.52.2`) 성공했지만, 바로 다음 스텝
`compile_lock.sh --verify`가 `committed requirements.lock has drifted
from requirements.txt`로 exit 1.

### 1.2 수정

Iteration 1과 동일한 올바른 절차로 재컴파일했다: `docker run --rm
--platform linux/amd64 -v "$PWD":/work -w /work python:3.11-slim bash -c
"pip install uv==0.8.15 && bash scripts/compile_lock.sh && bash
scripts/compile_lock.sh --verify"` — ubuntu-latest hosted runner와 동일한
linux/amd64 대상, 동일한 `uv==0.8.15`로 컴파일하고 같은 컨테이너 안에서
재현성까지 확인했다. 결과: 103개 패키지 유지(회귀 없음), `filelock`/
`uvicorn` 두 패키지만 버전·해시가 갱신됐고 `--verify PASS (reproducible,
no drift)`를 재확인했다.

### 1.3 `compile_lock.sh` 헤더 안정화(추가 개선)

재컴파일 diff를 검토하는 중, 커밋되는 매 lock 파일마다 autogenerated
헤더 주석의 `-o` 인자가 `uv`가 만든 절대 mktemp 경로 그대로 남는다는
점을 확인했다 — macOS에서는 `/var/folders/.../tmp.XXXX`, linux 컨테이너
안에서는 `/tmp/tmp.XXXX`로, 호스트/실행마다 달라진다. `--verify`의
`canonical_body()`가 이 헤더 줄을 비교에서 제외하므로 드리프트 감지
자체에는 영향이 없지만, 재컴파일할 때마다(내용이 완전히 같아도) 헤더
한 줄이 항상 바뀌어 diff 노이즈와 "이 lock이 어느 플랫폼/시점에
컴파일됐는지" 혼동을 유발한다 — 이번 세션 시작 시점에 발견한 §0의
오염된 로컬 lock(수동으로 다른 플래그를 붙여 macOS tmp 경로가 남은 채
커밋 직전까지 갔던 상태)이 정확히 이 인스턴스다. `compile_lock.sh`의
`compile_once()`에 정규화 단계를 추가했다 — 컴파일 직후 헤더 2번째
줄의 `-o <절대경로>`를 `-o requirements.lock`(고정 문자열)으로
치환한다. 재현성(`hash_a == hash_b`) 비교와 `--verify` 드리프트 비교
모두 원래부터 헤더를 제외하므로 이 정규화는 그 로직에 영향을 주지
않고, 커밋되는 최종 파일의 헤더만 호스트/플랫폼에 무관하게 결정론적으로
만든다. `--extra-index-url`/`--index-strategy unsafe-best-match` 등
기존 컴파일 인자는 전혀 바꾸지 않았다 — `torch==2.13.0+cpu`가 여전히
PyTorch CPU 인덱스에서 정확히 해석됨을 재확인했다(§4).

### 1.4 `compile_lock.sh` 헤더 계약 fail-closed 강화(Code_Review_Hosted_CI_Remediation_4.md CR-HCI4-MAJ-01 대응)

fresh Codex 리뷰(`Code_Review_Hosted_CI_Remediation_4.md`, FAIL 9.5, MAJOR
1건)가 §1.3의 헤더 정규화를 지적했다: `compile_once()`의 `awk`
`sub(/-o [^ ]+$/, repl)`는 2번째 줄이 예상 패턴과 맞을 때만 치환하고,
`sub()`이 0건을 치환해도 `awk`는 exit 0으로 끝난다. 즉 uv가 header 줄
위치를 바꾸거나, `-o` 뒤에 다른 토큰을 남기거나, `-o` 자체를 생략하거나,
banner를 중복 출력하면 mktemp 절대경로(또는 그보다 더 나쁜 임의 텍스트)가
그대로 "canonical" 산출물에 남는데도 스크립트는 성공으로 끝난다. 게다가
`--verify`는 `canonical_body()`로 모든 선행 `#` 줄을 제거한 뒤 body만
비교하므로, 커밋된 `requirements.lock`의 header가 임의로 손상돼 있어도
body만 같으면 PASS가 났다 — §1.3이 의도한 "최종 파일의 header를
호스트/플랫폼에 무관하게 결정론적으로 만든다"는 계약이 실제 gate로
고정되지 않은 상태였다.

**수정 (`scripts/compile_lock.sh`):**

1. `HEADER_LINE1`/`HEADER_PREFIX` 상수로 uv 출력의 정확한/제한된
   grammar를 고정했다 — 1번째 줄은 정확히 고정 banner 문자열이어야
   하고, 2번째 줄은 `HEADER_PREFIX` 뒤에 공백을 포함하지 않는 단일
   `-o` 인자만 와야 한다.
2. `validate_and_normalize_header()`가 치환 **전에** 이 grammar를
   검증하고, 1번째 줄 불일치·2번째 줄 prefix 불일치·`-o` 인자가
   비어있거나 뒤에 다른 토큰이 남는 경우·2번째 줄 이후 banner가
   중복 출현하는 경우를 모두 nonzero exit로 거부한다(fail-closed).
   grammar 검증을 통과한 경우에만 2번째 줄을 canonical 문자열로
   치환하고, 치환 직후 결과가 정확히 그 canonical 문자열인지 다시
   확인한다.
3. `validate_committed_header()`를 새로 추가해 `--verify`가 body
   동등성뿐 아니라 커밋된 `$LOCK_FILE`의 1/2번째 줄이 정확한 canonical
   형태인지도 검증하게 했다 — header가 손상되거나 stale mktemp
   경로가 남아 있으면 body가 같아도 `--verify`가 실패한다.

**결정론적 test (`tests/unit/test_compile_lock_header_contract.py`,
신규, 네트워크 없음):** 실제 `uv`를 fake `uv` bash 스크립트로 대체해
(환경변수 `FAKE_UV_SCENARIO`로 header 형태를 제어) 다음을 고정한다.

- 성공 경로: canonical header 생성 및 두 번 연속 실행 시 byte-for-byte
  동일한 출력(안정적 canonical 산출물).
- 실패(fail-closed) 경로 7종: header 전체 누락, banner 텍스트 상이,
  `-o` 플래그 누락, `-o` 뒤에 예기치 않은 토큰, `-o` 값이 빈 문자열,
  banner 중복 출력, header 블록 위치 이동 — 모두 nonzero exit,
  `requirements.lock` 미생성.
- `--verify` 경로: canonical header 위 PASS, 커밋된 header 2번째 줄이
  stale 경로로 변조된 경우 실패, 1번째 줄 banner가 손대진 경우도
  실패 — 각각 stderr에 `header` 관련 메시지 포함.

`canonical_body()`/reproducibility(`hash_a == hash_b`)/drift 비교
로직과 `--extra-index-url`/`--index-strategy unsafe-best-match` 등
compile 인자는 전혀 바꾸지 않았다. linux/amd64 `python:3.11-slim` +
`uv==0.8.15` 컨테이너에서 `bash scripts/compile_lock.sh && bash
scripts/compile_lock.sh --verify`를 재실행해 `--verify PASS
(reproducible, no drift)`를 재확인했고, `requirements.lock`의 diff는
§1.2와 동일(패키지 수/hash 변경 없음, header `-o` 인자만 canonical화)
하다.

### 1.5 exact two-line header grammar fail-closed 경계 완결
(Code_Review_Hosted_CI_Remediation_4_Iteration_2.md CR-HCI4-I2-MAJ-01 대응)

fresh Codex 재리뷰(`Code_Review_Hosted_CI_Remediation_4_Iteration_2.md`,
FAIL 9.5, MAJOR 1건)가 §1.4의 폐쇄를 불완전하다고 판정했다:
`validate_committed_header()`는 커밋된 `requirements.lock`의 1번째/
2번째 줄만 검사하고, `validate_and_normalize_header()`도 생성된
scratch 산출물의 3번째 줄 이후에서 정확히 배너 텍스트가 반복되는
경우만 찾는다. 두 경우 모두 `canonical_body()`가 모든 선행 `#` 줄을
제거한 뒤 body만 비교하므로, 3번째 줄에 임의의 새 comment/header
(예: `# unexpected third header line`)나 배너 전체의 중복(예: 헤더
2줄이 그대로 반복)이 끼어 있어도 body만 같으면 `--verify PASS`가
났다 — 독립 fake-uv probe로 두 변조 모두 exit 0을 재현해 확인했다.
Task가 요구한 "정확히 두 줄, 3번째 줄 이후 임의/중복 header를 모두
거부"라는 계약이 아직 gate로 고정되지 않은 상태였다.

**수정 (`scripts/compile_lock.sh`):**

1. 새 공용 함수 `assert_no_extra_header_lines()`를 추가했다 — 대상
   파일의 3번째 줄부터 끝까지 스캔해 `#`로 시작하는 줄이 하나라도
   있으면(임의의 unexpected comment든, 배너 전체의 재출현이든 구분
   없이) 그 줄 번호와 함께 nonzero exit로 거부한다. "정확히 두 줄의
   header, 3번째 줄은 반드시 첫 body 줄"이라는 단일 불변식으로 두
   변조 케이스를 한 번에 포섭한다.
2. `validate_and_normalize_header()`(생성 산출물 경로)의 기존
   line-3-이후 배너 전용 중복 검사를 제거하고, line 1/2 grammar
   검증 통과 직후 `assert_no_extra_header_lines()` 호출로 대체했다 —
   line 2 치환(정규화) 이전에 검증하므로 여전히 fail-closed다.
3. `validate_committed_header()`(`--verify` 경로)에도 line 1/2 exact
   일치 검증 뒤 동일한 `assert_no_extra_header_lines()` 호출을
   추가했다 — 생성 경로와 커밋 경로가 서로 다른 부분 검사로 다시
   갈라지지 않도록 하나의 함수를 재사용한다(리뷰 필수 조치 #2).

**결정론적 test 확장 (`tests/unit/test_compile_lock_header_contract.py`,
네트워크 없음, 12건 → 15건):**

- fake-uv 시나리오 `unexpected_third_header`를 추가해 compile 모드
  fail-closed parametrize(기존 7종 → 8종)에 편입했다 — 정확한 배너가
  아닌 임의의 3번째 `#` 줄도 nonzero exit·lock 미생성으로 거부됨을
  고정.
- `--verify` 모드에 두 test를 추가했다: 커밋된 lock의 3번째 줄에
  임의 comment를 삽입한 변조, 그리고 canonical 2줄 header 전체를
  그대로 반복 삽입한 변조 — 둘 다 nonzero exit·stderr에 `header`
  포함을 요구.
- **결함 재현으로 test 유효성 검증(mutation/defect detection):** 위
  세 신규 assertion을 로컬에서 `assert_no_extra_header_lines()` 호출
  두 곳만 주석 처리한 mutated 버전(CR-HCI4-I2-MAJ-01이 지적한 정확한
  이전 상태 재현)에 대해 실행 — 세 test 모두 `assert 0 != 0`으로
  실패(스크립트가 exit 0/`--verify PASS`를 냄)함을 확인해 신규 test가
  실제로 이 결함 클래스를 검출함을 입증했다. mutation을 되돌려 수정된
  스크립트로 재실행하면 15개 전부 PASS.

`canonical_body()`/reproducibility/drift 비교 로직, `--extra-index-url`/
`--index-strategy unsafe-best-match`/`--generate-hashes`/`--no-annotate`
compile 인자, §1.3/§1.4가 고정한 line 1/2 canonicalization·정규화
로직은 전혀 바꾸지 않았다. linux/amd64 `python:3.11-slim` + `uv==0.8.15`
컨테이너에서 `pip install uv==0.8.15 && bash scripts/compile_lock.sh &&
bash scripts/compile_lock.sh --verify` 재실행: **PASS**(`Resolved 103

## 2. `container_smoke.py` — readiness 폴링 예산 부족

### 2.1 원인

```json
{
  "host_gateway_reachable": true,
  "mock_query_ok": false,
  "production_test_seam_sealed": true,
  "readiness_sequence": {"live": true, "ready": false},
  "root_page_ok": true,
  "static_asset_ok": true,

```

`live=true`인데 `ready=false`라는 조합은 uvicorn 프로세스 자체는 정상
기동했지만 `/health/ready`가 요구하는 실제 준비 상태(설정 바인딩 확인,
아티팩트 해시 검증, FAISS/embeddings canary 쿼리)에 hosted runner에서
도달하지 못했다는 뜻이다. `run_smoke()`의 `_poll_ready(host_port,
expect_status=200)` 호출은 `max_seconds` 기본값 10초를 그대로 썼고, 바로
뒤 `mock_query_ok`도 아직 준비되지 않은 엔진에 쿼리를 보내므로 함께
실패했다.

로컬(Apple Silicon, `docker --platform linux/amd64`로 hosted와 동일한
아키텍처 타깃, Docker Desktop VM을 통한 Rosetta 변환)에서 같은 이미지를
빌드해 직접 시간을 측정했다:

- `docker run --entrypoint python <image> -c "import
  simple_qna_rag.rag_engine"`만 단독으로 **약 4.2초** — `rag_engine.py`가
  `langchain_huggingface.HuggingFaceEmbeddings`를 모듈 최상단에서
  무조건 import하므로(`EMBEDDING_PROVIDER=deterministic_test`이든 아니든
  무관), `torch`/`transformers`/`sentence-transformers` import 체인의
  콜드 비용이 provider 선택과 상관없이 항상 든다.
- 컨테이너 기동부터 `/health/ready`가 처음 200을 반환할 때까지 **약
  4.7초**.
- 로컬 전체 `run_smoke()` 실행(픽스처 빌드, 컨테이너 기동, 쿼리, negative
  control 컨테이너까지 포함) 총 **약 16~17초** — 모두 `status: PASS`.

즉 로컬(에뮬레이션 오버헤드 포함)에서도 준비까지 10초 예산의 절반
가까이를 쓴다. hosted GitHub Actions 러너는 공유 2 vCPU라 이 콜드 import
+ canary 검증 경로가 노이즈 이웃/스케줄링 변동에 따라 종종 10초를
넘는다 — hosted 로그의 전체 스크립트 실행 시간이 약 26.6초였다는 점(§2.1
로그 타임스탬프: 18:27:11.40 시작, 18:27:38.02 JSON 출력)도 일치한다.
negative control 경로(`production_test_seam_sealed=true`로 hosted에서도
성공)는 이 무거운 검증을 전혀 거치지 않는다 — 테스트 시임 모듈이 없어
`import` 단계에서 곧바로 실패해 503을 즉시 반환하므로, 같은 10초 예산
안에서도 항상 여유가 있다. 이 비대칭이 "ready만 실패하고 negative
control은 통과"라는 hosted 로그의 정확한 패턴을 설명한다. `b072fc9`가
바꾼 파일(`scan_image_layers.py`, 관련 테스트)은 서빙 경로
(`rag_engine.py`/`server.py`/`index/verification.py`)를 전혀 건드리지
않았으므로, 이번 실패는 코드 회귀가 아니라 hosted 러너 부하 변동에 의한
예산 부족이다.

### 2.2 수정

`scripts/container_smoke.py`의 포지티브 readiness 폴링 호출 한 곳만
`max_seconds=60`으로 늘렸다:

```python
ready_ok, _, _ = _poll_ready(host_port, expect_status=200, max_seconds=60)
```

- **fail-closed 성질은 그대로 보존된다** — 정말로 고장난 컨테이너는
  여전히 유한한 시간(60초) 안에 `ready_ok=False`로 떨어져 `status: FAIL`을
  낸다. 이번 변경은 판정 기준(상태 코드, `reason`, 5개 boolean, negative
  control의 `artifact_test_embedding_seam_unavailable` 503)을 하나도
  바꾸지 않고, 정상 컨테이너가 정상 지연 아래에서 오탐되지 않도록 시간
  여유만 넓혔다.
- negative control의 `_poll_ready(..., expect_status=503, ...)` 호출은
  건드리지 않았다 — §2.1에서 확인했듯 그 경로는 애초에 10초 예산 안에서
  항상 여유 있게 통과했고(hosted 로그의 `production_test_seam_sealed:
  true`), 변경할 근거가 없다.
- `.github/workflows/ci.yml`의 `container` job에는 step 단위
  `timeout-minutes`가 없다(job 기본 360분 한도만 적용) — 60초 예산 확장이
  워크플로 타임아웃과 충돌할 여지는 없다.
- `_poll_ready()`의 `max_seconds` 기본값(다른 호출부가 없어 지금은
  negative control 한 곳에만 남는다)과 시그니처는 바꾸지 않았고, 어떤
  단위 테스트도 `_poll_ready`의 특정 `max_seconds` 값에 의존하지 않는다.
